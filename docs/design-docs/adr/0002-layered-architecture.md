# ADR-0002: 도메인 슬라이스 + 6레이어 아키텍처

- **상태**: ACCEPTED
- **날짜**: 2026-09-06
- **관련**: [ARCHITECTURE.md](../../../ARCHITECTURE.md), [core-beliefs.md](../core-beliefs.md) CB-3, CB-10

## 맥락

에이전트는 이미 저장소에 있는 패턴을 복제한다. 초기에 구조를 고정하지 않으면
"컴포넌트 안에서 데이터 읽고 파싱하고 렌더하는" 패턴이 순식간에 전체로 퍼진다.
사람 팀이라면 리뷰로 잡겠지만, 처리량이 사람의 주의력을 넘어서면 리뷰는 병목이 된다.

앱이 둘이라 위험이 두 배다. 같은 실수를 두 곳에서 따로 하게 된다.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 관례만 문서화 | 유연함 | 강제되지 않음 → 드리프트 확정 |
| 타입별 폴더 (components/hooks/utils) | 익숙함 | 기능이 흩어져 도메인 추론 불가 |
| **도메인 슬라이스 + 고정 레이어 (채택)** | 경계가 기계 검사 가능, 도메인 단위 추론 | 초기 보일러플레이트 증가 |

## 결정

각 도메인은 `types → config → data → service → state → ui` 여섯 레이어를 가지며
의존성은 아래 방향으로만 흐른다. 횡단 관심사는 `providers` 인터페이스로만 들어온다.
도메인 간 직접 import 는 금지하고, 공유가 필요하면 `shared/`로 승격한다.

**두 앱이 같은 구조를 쓴다.** 한쪽에서 배운 것이 다른 쪽에 그대로 적용된다.

**강제 수단**: `npm run lint:arch`.
위반 시 에러 메시지에 "어느 레이어에서 어디로 갔고, 대신 무엇을 하라"를 함께 출력한다 (CB-3).

## 결과

- 좋아지는 것: 새 기능의 위치가 자명해진다. `/new-slice`로 스캐폴드가 가능해진다.
  파일 하나만 읽어도 그게 어느 레이어인지 알 수 있어 컨텍스트 비용이 준다
- 나빠지는 것: 작은 기능도 폴더가 여러 개 생긴다. **레이어가 비면 만들지 않는 것**으로 완화한다
- 사람 기준으로는 과할 수 있다. 에이전트 기준으로는 속도를 내기 위한 **선행 조건**이다

## 되돌리는 조건

6개월간 `state` 또는 `config` 레이어가 실사용되지 않으면 레이어 수를 줄이는 ADR 을 쓴다.
