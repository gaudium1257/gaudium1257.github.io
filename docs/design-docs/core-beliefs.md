# 핵심 신념 (Core Beliefs)

이 저장소는 **에이전트가 읽고 쓰는 것을 1순위로** 최적화한다.
아래는 다른 모든 규칙이 파생되는 상위 원칙이다. 충돌 시 이 문서가 이긴다.

---

## CB-1. 저장소 밖 지식은 존재하지 않는다

에이전트 관점에서 실행 중 컨텍스트로 가져올 수 없는 것은 **없는 것**이다.
대화, 메모 앱, 머릿속에 있는 결정은 접근 불가능하다.
따라서 결정을 내렸다면 **버전 관리되는 아티팩트(코드·마크다운·스키마·계획)로 남긴 뒤** 진행한다.

기준: *"3개월 뒤 합류한 사람이 저장소만 보고 알 수 있는가?"* 아니라면 문서화가 덜 된 것이다.

## CB-2. 지도를 줘라, 매뉴얼을 주지 마라

거대한 지침 파일은 예측 가능하게 실패한다.
컨텍스트는 희소 자원이고, 모든 게 중요하면 아무것도 중요하지 않으며, 큰 문서는 낡은 규칙의 무덤이 된다.

→ `CLAUDE.md`는 **목차**다 (200줄 상한, 린터가 강제). 깊은 내용은 `docs/`와 스킬에 두고 링크만 건다.
→ 에이전트는 작고 안정적인 진입점에서 시작해 필요한 만큼만 파고든다 (프로그레시브 디스클로저).

## CB-3. 불변식은 강제하고, 구현은 자유롭게 둔다

문서만으로는 일관성이 유지되지 않는다. 중요한 경계는 **린터·구조 테스트·훅으로 기계화**한다.
그 대신 경계 안쪽 구현은 마이크로매니징하지 않는다.

예: "경계에서 데이터를 파싱하라"는 강제한다. "Zod를 써라"는 강제하지 않는다.

린트 에러 메시지에는 **고치는 방법**을 함께 적는다. 에러 메시지가 곧 에이전트 컨텍스트다.

## CB-4. 계획은 일급 아티팩트다

작은 변경은 즉흥 계획으로 충분하다. 복잡한 작업은 `docs/exec-plans/`에 진행 상황과 결정 로그와 함께 저장한다.
활성·완료·기술부채가 모두 같은 곳에 버전 관리되어야 에이전트가 외부 맥락 없이 이어서 일할 수 있다.

## CB-5. 애플리케이션을 에이전트가 읽을 수 있게 만든다

사람의 QA 시간이 병목이다. 그러니 **UI·로그·상태를 에이전트가 직접 읽고 검증할 수 있게** 만든다.
브라우저로 실제 렌더를 확인하고 (`/ui-verify`), 콘솔 에러를 읽고, 상태 코드를 실측한다.
"보기엔 맞을 것 같다"로 끝내지 않는다.

## CB-6. 막힘은 신호다

에이전트가 헤매면 "더 열심히"가 답이 아니다. **환경이 덜 갖춰진 것**이다.
빠진 도구·추상화·문서를 먼저 만들고, 그 수정을 저장소에 되돌려 넣는다.
그 작업이 기능 구현보다 우선순위가 높은 경우가 많다.

## CB-7. 지루한 기술을 고른다

결합도가 낮고 API가 안정적이며 학습 데이터에 잘 표현된 기술이 에이전트가 모델링하기 쉽다.
불투명한 업스트림 동작에 끌려다니느니, 필요한 부분만 직접 구현하는 게 쌀 때가 있다.
직접 구현할 땐 테스트로 완전히 덮는다.

새 의존성은 **정당화**한다. 특히 공개 사이트에 들어가는 것은 더 엄격히 본다.

## CB-8. 엔트로피는 매일 조금씩 갚는다

에이전트는 저장소에 이미 있는 패턴을 — 나쁜 패턴까지 — 복제한다. 드리프트는 필연이다.
주간 대청소는 확장되지 않는다. `/doc-gardening`과 정기 정리로 **매일 조금씩** 갚는다.
기술 부채는 고금리 대출이다.

## CB-9. 사람의 취향은 시스템으로 되먹인다

리뷰 코멘트, 리팩터 요청, 버그 리포트는 **문서 갱신이나 린트 규칙으로 인코딩**한다.
문서로 부족하면 규칙을 코드로 승격한다. 같은 지적을 두 번 하게 만들지 않는다.

## CB-10. 앱이 둘이면 진실은 하나여야 한다

`viewer` 와 `admin` 은 별개 앱이지만 **같은 콘텐츠를 다룬다.**
개념을 두 번 정의하는 순간 드리프트가 시작되고, 에이전트는 한쪽만 보고 고친다.
공유해야 할 것(스키마·도메인 어휘)은 반드시 `shared/` 에 하나만 둔다 (INV-9).
공유하면 안 되는 것(쓰기 경로)은 확실히 갈라 둔다 (INV-8).
