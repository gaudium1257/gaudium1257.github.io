# TESTING.md — 테스트 전략

## 무엇을 테스트하는가

에이전트의 처리량이 사람의 QA 를 넘어선다. 테스트는 **사람 대신 보는 눈**이다.
따라서 "커버리지 숫자"가 아니라 **회귀하면 아픈 것**을 덮는다.

| 대상 | 도구 | 반드시 테스트 |
|---|---|---|
| 스키마·파싱 (`shared/content`, `data`) | Vitest | **필수.** 잘못된 입력이 거부되는지 |
| 비즈니스 규칙 (`service`) | Vitest | **필수.** 순수 함수라 싸다 |
| 검색 인덱스·조회 | Vitest | **필수.** 결과 없음·부분 일치 동작 |
| 테마 프로바이더 | Vitest | 저장소 접근 불가 시에도 동작하는지 (스펙 T-4) |
| 훅 (`state`) | Vitest + Testing Library | 조건 분기가 있으면 |
| 컴포넌트 (`ui`) | Testing Library | 사용자 상호작용이 있으면 |
| 아키텍처 불변식 | `lint:arch` | 자동 |

## 어떻게 쓰는가 (GR-8)

- **관찰 가능한 동작**을 검증한다. 내부 상태·호출 횟수가 아니라 화면에 보이는 결과
- 쿼리는 접근성 기준으로: `getByRole` > `getByLabelText` > `getByText`. `data-testid` 는 최후
- 테스트 이름은 **조건과 기대 결과**를 문장으로: `"검색 결과가 없으면 안내 문구를 보여준다"`
- 목(mock)은 경계에서만. `service` 를 목하지 말고 실제로 호출한다
- 실제 개인정보·토큰을 픽스처에 넣지 않는다 (INV-7)

## 하면 안 되는 것 (INV-4 위반의 흔한 형태)

- 실패하는 테스트를 `skip` 처리하고 넘어가기
- 구현을 바꾸지 않고 기대값만 수정해서 통과시키기
- 단언 없는 테스트 ("에러 안 나면 통과")

테스트가 실패했는데 원인을 모르겠다면, 그건 **막힌 것**이다 (CB-6).
우회하지 말고 무엇이 부족한지 먼저 파악한다.

## 플레이키 테스트

간헐적 실패는 즉시 원인을 찾거나, 못 찾으면 `tech-debt-tracker.md` 에 P1 로 등록한다.
조용히 재시도로 덮지 않는다.
