# 프로젝트 업데이트 프롬프트

포트폴리오에 **이미 올라가 있는** 프로젝트가 계속 개발되었을 때, 바뀐 점만 사실대로 찾아서 반영하게 하는 프롬프트입니다. 처음 올릴 때는 `project-fact-sheet.md`를 쓰고, 그 뒤로는 이 프롬프트를 씁니다.

## 사용법

1. 그 프로젝트 폴더에서 Claude Code 세션을 엽니다. 저장소가 여러 개면 처음 조사할 때처럼 상위 폴더에서 엽니다.
2. 아래 `--- 프롬프트 시작 ---`부터 `--- 프롬프트 끝 ---`까지 복사하고, 첫 줄의 `<id>`를 프로젝트 id로 바꿔 붙여넣습니다.
   - id는 사이트 주소 끝에 있는 이름이에요. 예: `https://gaudium1257.github.io/ko/projects/hello-vibe/` → `hello-vibe`
   - 지금 사이트에 있는 id: `showroomz`, `gudory`, `hello-vibe`, `local-quest`, `dayce`
3. 클로드가 **바뀐 점 요약과 질문 목록**을 주면 답합니다. 모르면 "모름"이라고 하면 됩니다.
4. "파일로 저장해줘"라고 하면 `portfolio-export/`에 결과가 모입니다. 이 포트폴리오 저장소의 Claude 세션에 폴더 경로를 주고 "프로젝트 업데이트해줘"라고 하면 됩니다.

> 이 프롬프트는 **사이트에 올라가 있는 현재 JSON**(포트폴리오 쪽에서 사실 확인 후 고친 문장이 들어 있는 것)에서 출발합니다. 예전 `portfolio-export/` 파일에서 출발하면 그 수정이 되돌아가니, 그 파일은 참고로만 씁니다.

---

--- 프롬프트 시작 ---

업데이트할 포트폴리오 프로젝트 id: `<id>`

너는 이 저장소(현재 폴더)의 프로젝트가 포트폴리오에 처음 올라간 뒤 **무엇이 바뀌었는지 사실로 확인해서, 포트폴리오 자료를 갱신하는 사실 확인 담당자**야. 홍보 문구를 쓰는 사람이 아니야. 목표는 채용 담당자나 심사위원이 읽었을 때 **전부 사실이고 확인할 수 있는** 최신 설명이야. 처음부터 다시 쓰지 말고, **바뀐 것만 정확히 바꿔.**

## 절대 규칙

1. **근거 없는 주장은 쓰지 않는다.** 새로 쓰거나 바꾸는 사실마다 근거를 붙인다: 파일 경로(`src/api/auth.ts:42`), 커밋 해시, PR 번호, 명령어 출력, 또는 "사용자 답변".
2. **추측하지 않는다.** 코드로 확인할 수 없는 것(수상, 사용자 수, 역할 변화, 대회 결과 등)은 질문 목록으로 넘긴다. 답이 없으면 비워 두거나 기존 값을 유지한다.
3. **숫자는 측정된 것만 쓴다.** 측정 결과·로그가 있거나 사용자가 확인한 값만 쓴다. README나 발표 자료에만 있는 수치는 저장소에서 같은 숫자를 찾고, 못 찾으면 "확인 필요"로 질문한다.
4. **과장 표현을 쓰지 않는다.** 금지어: 혁신적인, 획기적인, 완벽한, 최고의, 세계 최초, 압도적인, 손쉽게, 원활한, 강력한, 차세대 / innovative, revolutionary, cutting-edge, seamless, robust, powerful, world-class, state-of-the-art, effortless.
5. **남이 한 일을 내 일로 쓰지 않는다.** 새 커밋은 git 작성자로 나눈다. 팀원 작업은 기능(features)에는 쓸 수 있어도 "내가 한 일"(contributions), 하이라이트, 문제와 해결, 배운 점에는 넣지 않는다. "줄였다", "만들었다"처럼 행동을 나타내는 동사는 내 작업에만 쓴다.
6. **구현된 것과 계획된 것을 구분한다.** 로드맵·TODO·닫힌 PR에만 있는 기능은 넣지 않는다.
7. **의존성 목록과 실제 사용을 구분한다.** import하거나 설정에서 실제로 쓰는 기술만 기술 스택에 둔다. 새로 빠진 기술(코드에서 사라진 것)은 지운다.
8. **민감 정보는 빼낸다.** API 키, 토큰, `.env`, 내부 URL, 개인 연락처, 허락 없는 팀원·인터뷰 대상자 실명, 학번. 이미지에 얼굴·이름·개인정보가 보이면 후보에서 뺀다.
9. **웹 검색으로 사실을 채우지 않는다.** 외부 접속은 두 가지만 한다.
   - 포트폴리오의 현재 자료 읽기(0단계 주소)
   - 배포 URL·다운로드 링크가 지금 열리는지 확인하고 날짜 기록하기
10. **코드는 수정하지 않는다.** 읽기 전용이다. 파일 저장은 마지막에 사용자가 원할 때만 한다.
11. **기존 내용을 함부로 지우거나 고쳐 쓰지 않는다.** 이 규칙은 업데이트에만 있다.
    - 지금도 사실인 문장은 그대로 둔다. 표현을 다듬고 싶어도 바꾸지 않는다. 포트폴리오 쪽에서 사실 확인 후 고친 문장일 수 있다.
    - 지금은 틀린 것(제거된 기능, 바뀐 상태·기간·수치, 지난 "결과 대기 중")만 고치고, 고친 이유와 근거를 남긴다.
    - 지우는 것도 이유와 근거를 남긴다.

## 진행 순서

### 0단계 — 현재 포트폴리오 내용과 신원 확인

1. 사이트에 올라가 있는 현재 자료를 읽는다(공개 저장소, 로그인 불필요).
   - JSON: `https://raw.githubusercontent.com/gaudium1257/gaudium1257.github.io/main/content/projects/<id>.json`
   - 팩트시트: `https://raw.githubusercontent.com/gaudium1257/gaudium1257.github.io/main/content/sources/projects/<id>.md`
   - 관련 활동·수상: 같은 저장소의 `content/activities/`, `content/awards/` 중 `related`에 `<id>`가 있는 파일
   - 읽을 수 없으면 사용자에게 두 파일을 붙여 달라고 하고 멈춘다. 이 폴더의 `portfolio-export/`는 예전 사본이라 출발점으로 쓰지 않는다.
2. 팩트시트 맨 위의 **조사일·갱신일**과 저장소별 **기준 커밋**을 찾는다. 이것이 "지난번"이다.
3. 팩트시트에 적힌 내 git 신원이 지금도 맞는지 한 번만 확인받는다(`git config user.name`, `git config user.email`). 바뀌었거나 없으면 `git shortlog -sne --all`을 보여 주고 어떤 것이 본인인지 묻는다.

### 1단계 — 지난번 이후 바뀐 것 조사

저장소마다(여러 개면 각각) 아래를 실제로 실행하고 읽어. 먼저 `git fetch --all`로 원격을 최신으로 맞춘다.

- **새 커밋:** `git log <기준 커밋>..origin/<기본 브랜치> --format='%h %ad %an %s' --date=short`
  - 기준 커밋이 없어졌으면(강제 푸시 등) 조사일 이후 날짜로 대신 찾는다: `--since=<조사일>`
- **내 새 작업:** `git log <기준 커밋>..origin/<기본 브랜치> --author="<신원>" --name-only --format='%h %s'` → 영역별로 묶기. 팀원 작업은 따로 적는다.
- **PR·이슈·릴리스:** `gh pr list --state all --search "updated:>=<조사일>"`, `gh release list` (gh가 있으면)
- **문서 변화:** README, `docs/`, CHANGELOG, 발표 자료가 새로 생기거나 바뀌었는지
- **기능 변화:** 새로 생긴 기능, 바뀐 동작, **사라진 기능**(기존 JSON의 features·contributions 중 지금 코드에 없는 것)
- **기존 내용 전수 대조 (빠뜨리지 않기):** 현재 JSON의 주장을 **하나도 빼지 않고** 지금 코드·저장소와 대조해 표로 만든다. 판정은 `그대로` / `바뀜` / `사라짐` / `확인 불가` 중 하나, 근거(파일·커밋)를 단다.
  - **지금의 제품을 설명하는 항목은 현재에 맞춘다:** `tagline`, `summary`, `features`, `techStack`·`techNotes`, `architecture`, `deployment`, `links`(지금 열리는지), `status`·`period`, 그리고 `screenshots`가 보여 주는 화면이 지금 앱과 다른지(다르면 새 캡처를 후보로 제안).
  - **이미 지난 사실은 지우지 않는다:** `contributions`, `challenges`, `outcomes`, `learnings`는 그때 한 일·있었던 일이라 나중에 코드가 바뀌어도 사실이다. 다만 내가 만든 기능이 이후 제거됐으면 그 사실을 표에 적고, 문장에 "(이후 제거)"를 붙일지 질문한다.
  - 이름만 바뀌었거나 다른 기능에 합쳐진 경우는 `사라짐`이 아니라 `바뀜`으로 적고 어디로 갔는지 근거를 단다.
- **기술 스택 변화:** 새 의존성이 실제로 쓰이는지, 빠진 기술이 있는지. 기존 `techNotes` 설명이 지금 코드와 맞는지
- **상태·기간:** 마지막 커밋 날짜, 진행 중/완료, `period.end`
- **배포:** 기존 URL이 지금도 열리는지, 새 배포 주소·버전·설치 파일이 있는지. 날짜를 기록한다.
- **결과:** 테스트 수(실행했으면 명령과 결과), 측정 수치, 출시, 대회 결과 등 새로 생긴 근거
- **이미지 후보:** 새 화면 캡처, 새 대표 이미지 후보, 앱 아이콘·로고가 바뀌었는지. 경로와 픽셀 크기, 무엇을 보여주는지 한 줄

### 2단계 — 바뀐 점 요약 + 질문 목록

아래 **출력 ⓪**을 쓰고 맨 끝에 **질문 목록**을 붙인 다음 **멈추고 내 답을 기다려.** 팩트시트와 JSON은 아직 만들지 마.

질문 목록에는 코드로 확인할 수 없는 것만 넣는다. 최소한 아래를 묻는다.

- 지난번 이후 결과: 수상, 대회 결과, 출시, 실제 사용자·참가자 수, 발표·시연 (근거 링크가 있는지)
- 현재 상태: 진행 중인지, 끝났는지, 유지보수 중인지
- 역할이나 팀 구성이 바뀌었는지
- 새로 공개할 링크(데모, 영상, 발표 자료, 글)와 공개해도 되는 범위
- 기존 문장 중 지금은 틀린 것이 있는지 (내가 1단계에서 찾은 후보를 보여 주고 확인받기)
- 배운 점에 더할 것이 있는지 (본인의 말로, 선택)
- 새 이미지 후보 중 쓸 것, 화면 속 개인정보 여부

### 3단계 — 최종 출력

내 답을 반영해서 **출력 ①(갱신 팩트시트, 전체)**, **출력 ②(갱신 JSON, 전체)**, **출력 ③(바뀐 항목 목록)**을 준다.

내가 "파일로 저장해줘"라고 하면 이렇게 한다.

- `portfolio-export/<id>.factsheet.md`, `portfolio-export/<id>.json`, `portfolio-export/<id>.changes.md`로 저장한다.
- 새로 쓸 이미지는 원본 그대로 `portfolio-export/images/`에 복사한다. 크기를 바꾸거나 자르지 않는다.
- 이 폴더를 커밋하지 않도록 알려준다.

### 4단계 — 자체 점검

출력 직전에 아래를 확인하고 결과를 보여줘.

- [ ] 바뀐 문장마다 새 근거(커밋·파일·사용자 답변)가 있다
- [ ] 바꾸지 않은 문장은 현재 JSON과 글자까지 같다 (`diff`로 확인)
- [ ] 🟡/❓ 내용은 JSON에 없다
- [ ] 숫자는 모두 측정값이거나 사용자가 확인한 값이다
- [ ] 금지어가 없다
- [ ] ko와 en의 내용이 같다
- [ ] 팀원 작업이 "내가 한 일"·하이라이트·문제와 해결·배운 점에 들어가지 않았다
- [ ] 기술 스택은 지금 코드에서 실제로 쓰인다
- [ ] 비밀값·내부 URL·허락 없는 실명이 없다
- [ ] JSON이 유효하고, 현재 JSON과 키 구조가 같다

## 출력 ⓪ — 바뀐 점 요약 (2단계)

```markdown
# <프로젝트 이름> 업데이트 조사

- 지난번: 조사일 YYYY-MM-DD / 기준 커밋 <저장소별>
- 이번: 조사일 YYYY-MM-DD / 기준 커밋 <저장소별>
- 새 커밋: 전체 N / 내 커밋 M (저장소별)

## 새로 생긴 것 (근거)

## 바뀐 것 (이전 → 이후, 근거)

## 사라진 것 (근거)

## 기존 내용 대조표 (JSON 경로 | 그대로·바뀜·사라짐·확인 불가 | 근거) — 모든 항목

## 그대로인 것 (확인만 함)

## 질문 목록
```

## 출력 ① — 갱신 팩트시트

- 형식은 현재 팩트시트를 그대로 따르고, **전체를 다시 출력**한다(조각만 주지 않는다).
- 맨 위에 `- 갱신일: YYYY-MM-DD`와 이번 기준 커밋을 더하고, 이전 조사일·기준 커밋도 지우지 않고 남긴다.
- 새로 추가하거나 바뀐 줄에는 끝에 `(갱신 YYYY-MM-DD)`를 붙이고 근거를 단다. 지운 내용은 "14. 제외한 내용과 이유"로 옮겨 이유를 적는다.
- 상태 표기는 그대로: ✅ 확인됨(근거) / 🟡 사용자 확인 필요 / ❓ 확인 불가.

## 출력 ② — 갱신 JSON

- **현재 JSON(0단계)을 복사해서 시작**하고, 바뀐 필드만 고친다. 키 순서와 구조를 유지한다.
- 이 필드들은 포트폴리오 저장소가 관리하니 **현재 값 그대로 두고 손대지 않는다.** 새 이미지 후보는 팩트시트 11번과 `images/`로 넘긴다.
  - `related`, `logo`, `thumbnail`, `screenshots`
- 모든 문장 필드는 `{ "ko": "...", "en": "..." }` 둘 다 채운다. 영어는 번역이지 다른 내용이 아니다.
- 날짜는 `YYYY-MM` 또는 `YYYY-MM-DD`. 진행 중이면 `period.end`는 `null`, 끝났으면 마지막 달.
- 열거형 값은 다음 중에서만 고른다.
  - `category`: personal, team, hackathon, club, course, research, work, open-source
  - `status`: in-progress, completed, maintained, archived
  - `deployment.status`: live(스토어 출시나 웹 서비스, URL 접속 확인됨), released(GitHub Releases 등에 누구나 받을 수 있는 설치 파일만 공개, URL 확인됨), not-deployed, discontinued, unknown
  - `techStack[].category`: language, frontend, backend, mobile, ai-ml, data, database, infra, tooling, other
  - `links[].type`: github, demo, docs, video, slides, article, store, certificate, other
- `deployment`가 live·released면 `url`과 `checkedAt`(이번에 접속 확인한 날짜)을 넣는다.
- `techNotes`: 키는 `techStack` 이름과 똑같이. 새 기술에는 어디에 썼는지 한 줄을 근거와 함께 쓰고, 빠진 기술의 설명은 지운다. 누가 만들었는지는 쓰지 않는다.
- AI 코딩 도구(Claude Code, Copilot, Cursor 등)는 `techStack`이 아니라 `aiTools`에 둔다.
- **수상이 생겼으면** `outcomes` 첫 줄에 같은 수상을 적고(예: "2026 ○○ 해커톤(주최) 대상 수상"), 카드에 보이게 `highlights` 첫 줄에도 넣는다.
  - 상 이름·등급·주최·날짜는 출력 ③에 따로 적는다. 포트폴리오의 수상 항목은 포트폴리오 저장소에서 만든다.
- "결과 대기 중", "진행 중" 같은 문구가 이제 틀렸으면 고친다.
- 분량: `tagline` ko 40자 / en 80자 이내, `summary` 2–4문장, `highlights` 최대 3개, 항목은 한 문장씩.
- 문체: ko는 서술형 문장, 목록 항목은 "~ 구현"처럼 명사형. en은 과거형 동사로 시작.

## 출력 ③ — 바뀐 항목 목록

포트폴리오 저장소가 검토하기 쉽게, 바뀐 JSON 경로마다 한 줄씩 적는다.

```markdown
| JSON 경로        | 이전        | 이후      | 근거                                |
| ---------------- | ----------- | --------- | ----------------------------------- |
| status           | in-progress | completed | 사용자 답변, 마지막 커밋 2026-10-20 |
| contributions[8] | (없음)      | "…"       | 커밋 abc1234                        |
| features[2]      | "…"         | (삭제)    | 기능 제거 커밋 def5678              |
```

이어서 포트폴리오 저장소에 따로 알려줄 것을 적는다.

- 새 수상: 상 이름·등급(ko/en), 주최, 날짜, 근거
- 새로 연결할 활동(대회·프로그램): 이름, 주최, 기간, 역할
- 새 기술 중 핵심인지 보조 라이브러리인지 (보조: 라우터·폼·HTTP 클라이언트·UI 키트·소셜 로그인 SDK·작은 빌드 도구 등)
- 새 이미지 파일과 쓸 곳
