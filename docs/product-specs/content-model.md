# 스펙: 콘텐츠 데이터 모델

- **상태**: DRAFT — **사용자 입력 필요**
- **관련**: [ADR-0003](../design-docs/adr/0003-content-store.md), [EP-0001](../exec-plans/active/0001-bootstrap-scaffold.md)

> 이 문서가 확정되어야 `src/shared/content`의 Zod 스키마를 쓸 수 있다.
> 스키마는 **읽기(공개 모드)와 쓰기(관리자 모드) 양쪽이 통과하는 단일 진실 원천**이다.
> 확정 전까지 아래는 **가설**이다.

## 사용자에게 확인해야 할 것

- [ ] 1차 엔티티는 무엇인가? (아래는 가설)
- [ ] 각 엔티티에 반드시 들어가야 할 필드는?
- [ ] "프로젝트 리뷰"는 프로젝트의 일부인가, 별도 글인가?
- [ ] 지원 대상(학회 / 기업)에 따라 다른 구성을 보여줘야 하는가?

## 가설 엔티티

| 엔티티 | 설명 | 핵심 필드(가설) |
|---|---|---|
| `Profile` | 본인 소개 | 이름, 한 줄 소개, 소속, 연락 수단, 프로필 이미지 |
| `Project` | 만든 것 | 제목, 기간, 역할, 요약, 본문(마크다운), 기술스택, 링크, 이미지, 성과 |
| `Post` | 글 · 프로젝트 리뷰 · 회고 | 제목, 작성일, 분류, 본문(마크다운), 연결된 프로젝트 |
| `Experience` | 경력·활동 | 조직, 직함, 기간, 성과 |
| `Education` | 학력 | 기관, 전공, 기간 |
| `Award` | 수상·자격 | 이름, 수여기관, 날짜 |
| `Skill` | 기술 | 이름, 분류, 숙련도 |

## 저장 형태

`content/` 에 JSON 으로 커밋된다 ([ADR-0003](../design-docs/adr/0003-content-store.md)).
긴 본문은 JSON 안의 마크다운 문자열로 둔다 — 파서를 하나로 유지하기 위해서다.

```
content/
├── profile.json
├── projects/<id>.json
├── posts/<id>.json
└── assets/…
```

## 공통 규칙 (가설)

- 모든 엔티티는 안정적인 `id`를 가진다 (URL과 정렬에 쓰인다). **한 번 정해지면 바꾸지 않는다**
- 시간 필드는 ISO 8601 문자열로 저장하고, 표시 형식은 `ui` 레이어에서 정한다
- `visibility` 필드로 공개/비공개를 제어한다 — 관리자 모드에서만 편집 가능 (INV-11)
  ⚠️ **`visibility: private` 는 화면에서 숨길 뿐 파일은 공개 리포지터리에 그대로 있다.**
  정말 감춰야 할 내용은 아예 넣지 않는다 ([SECURITY.md §6](../SECURITY.md))
- 정렬 순서는 데이터에 명시한다. 배열 순서에 의존하지 않는다
- 마크다운 본문은 렌더 시 **반드시 새니타이즈**한다 ([SECURITY.md §4](../SECURITY.md))

## 미결정이 미치는 영향

이 스펙이 DRAFT인 동안 `src/shared/content` 스키마는 **최소 필드로만** 만들고,
추측으로 필드를 늘리지 않는다 (PRODUCT_SENSE: 추측 기반 확장성 금지).
