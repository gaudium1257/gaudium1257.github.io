# WORKFLOW.md — 작업 흐름

## 한 사이클

```
지도 읽기 → 계획 → 구현 → 검증 → 자가 리뷰 → 기록
```

각 단계의 도구는 `CLAUDE.md §5`와 `.claude/skills/`에 있다.

## 브랜치

- 기본 브랜치에 직접 커밋하지 않는다. 작업 브랜치를 판다
- 브랜치 이름: `feat/<slug>`, `fix/<slug>`, `docs/<slug>`, `chore/<slug>`
- 한 브랜치 = 한 가지 일 (GR-10)

## 커밋

- 명령형 현재형 제목 한 줄 + 필요하면 본문에 **왜**
- 검증이 깨진 상태로 커밋하지 않는다
- **사용자가 요청하지 않으면 커밋·푸시하지 않는다**

## PR

PR 본문에 담을 것:
1. 무엇을 왜 바꿨는가
2. 어떻게 검증했는가 (`verify` 결과, `/ui-verify` 스크린샷)
3. 관련 exec-plan / ADR 링크
4. 남긴 부채 (tech-debt-tracker 항목 번호)

## 리뷰

1. **자가 리뷰 먼저** — `/self-review`로 골든 룰 대조. 스스로 먼저 읽지 않은 코드를 리뷰에 올리지 않는다
2. 지적을 받으면 고치는 것으로 끝내지 말고, **같은 지적이 반복되지 않게 시스템에 인코딩**한다 (CB-9)
   - 문서로 충분하면 `docs/` 갱신
   - 반복될 것 같으면 린트 규칙으로 승격 (`tools/lint/`)
3. 판단이 필요한 것만 사람에게 올린다

## 막혔을 때 (CB-6)

같은 접근으로 두 번 실패하면 멈춘다. 그리고 묻는다:

> **"무엇이 없어서 막혔는가?"**

빠진 것이 도구면 도구를, 문서면 문서를, 가드레일이면 가드레일을 먼저 만든다.
그리고 그 수정을 저장소에 되돌려 넣는다. 이게 이 저장소의 진짜 작업이다.
