# DESIGN.md — 비주얼 디자인과 디자인 시스템

## 이 사이트가 주는 인상

독자는 **학회 심사위원과 채용 담당자**다. 짧은 시간에 훑는다.
목표는 "화려함"이 아니라 **읽히는 것**이다.

- 정보 위계가 첫눈에 보인다 (무엇을 했나 → 어떤 역할이었나 → 결과가 무엇인가)
- 스크롤 없이 첫 화면에서 "이 사람이 누구인지"가 파악된다
- 인쇄/PDF 로 저장해도 무너지지 않는다 (심사자는 종종 그렇게 본다)

viewer 와 admin 은 **의도적으로 다르게 생겼다**. viewer 는 작품, admin 은 도구다.
admin 은 밀도 높고 실용적으로 — 예쁘게 만드는 데 시간을 쓰지 않는다.

## 레이아웃 폭

셸은 `viewer/src/app/layout.ts` 의 `SHELL` 하나로 통일한다 — 헤더와 본문이 같은 폭을 써야
세로선이 맞는다. 폭은 `max-w-6xl`(1152px).

> 처음에 `max-w-4xl`(896px) 이었는데 넓은 화면에서 좌우 여백이 과해 본문이 떠 보였다.
> 다만 **긴 글은 `PROSE_WIDTH`(max-w-3xl) 로 따로 좁힌다** — 한 줄이 너무 길면 눈이 다음 줄을 놓친다.
> 셸을 넓히는 것과 글줄을 넓히는 것은 다른 문제다.

## 강조색 (brand)

`--color-brand` 는 **링크·활성 탭·카드 강조·주요 버튼에만** 쓴다.
남발하면 강조가 아니게 된다. 본문과 보조 텍스트는 foreground/muted 를 쓴다.

그라디언트처럼 색 연산이 필요한 것은 `styles.css` 에 유틸(`.hero-surface`)로 둔다 —
컴포넌트에 쓰면 하드코딩된 색이 되어 린터가 막고, 다크 모드에서도 깨진다.

## 상단 배너

사이트의 뼈대다. 동작 스펙은 → [navigation-shell.md](product-specs/navigation-shell.md)

- 현재 위치한 탭이 **명확히** 보여야 한다. 색만으로 구분하지 않는다 (굵기 + 강조색 밑줄)
- 활성 표시는 **요소 안쪽**에 둔다. 밖으로 삐져나가면 nav 에 스크롤바가 생긴다 (실제로 겪음)
- 우상단 도구 2개(검색·테마)는 아이콘만으로 두지 않는다. 접근 가능한 이름을 반드시 준다
- 스크롤해도 배너가 방해되지 않아야 한다

## 모노레포 함정 — 공유 UI 가 Tailwind 스캔에서 빠진다

Tailwind v4 는 CSS 파일 기준으로 소스를 자동 탐지한다. vite root 가 `viewer/` 라서
**`shared/ui` 의 클래스는 기본적으로 생성되지 않는다** — 클래스는 DOM 에 붙어 있는데
CSS 규칙이 없어 레이아웃이 조용히 깨진다 (콘솔 에러도 나지 않는다).

각 앱의 `styles.css` 에 다음이 반드시 있어야 한다:

```css
@source '../../../shared/ui';
```

공유 UI 를 새로 쓰는 앱을 추가하면 이것부터 확인하라. `/ui-verify` 로 실제 렌더를 보면 드러난다.

## 토큰 — 다크 모드가 여기에 달려 있다

색·타이포·간격은 **테마 토큰으로만** 표현한다.

**컴포넌트 안에 하드코딩된 hex, `rgb()`, 매직 `px` 금지 — 린터가 잡는다.**
이유: 테마 토글이 토큰만 바꾸기 때문이다. 하드코딩된 색은 다크 모드에서 그대로 남아 깨진다.

다크 모드는 **토큰 레벨에서 해결**하고, 컴포넌트에 `isDark` 분기를 넣지 않는다.
두 테마 모두에서 대비 기준을 만족해야 한다 (스펙 T-5).

## shadcn/ui 사용 규범 (INV-6)

shadcn 은 라이브러리가 아니라 **코드 생성기**다.

1. 컴포넌트 추가는 **`npm run ui:add <name>`** 로만 (→ `/add-ui-component` 스킬)
2. 생성물(`**/components/ui/**`)은 **손으로 고치지 않는다.** 훅이 편집을 차단한다
3. 커스터마이즈가 필요하면:
   - 색·간격·라운드 → **테마 토큰**에서
   - 동작·조합 → `shared/ui/` 에 **래퍼 컴포넌트**
   - 그래도 안 되면 ADR 을 쓰고 생성물을 fork 한다 (마지막 수단)
4. 앱에서는 `shared/ui` 배럴을 통해 import 한다. `components/ui/` 를 직접 가리키지 않는다
5. **쓰지 않는 컴포넌트는 두지 않는다** (GR-9). 필요해지면 다시 가져온다

## 편집 폼

필드 명세는 `admin/src/domains/editor/config/forms.ts` 한 곳에 있다.
**스키마가 아니라 UI 메타데이터다** — 검증은 언제나 `shared/content` 의 Zod 가 한다 (INV-9).

스키마에 필드를 추가하고 폼에 빠뜨리면 **편집할 수 없는 필드**가 조용히 생긴다.
`forms.test.ts` 가 두 목록이 어긋나면 실패시킨다 (CB-3).

입력 규칙:
- 날짜는 달력 입력. 비우면 null → "진행 중"으로 표시된다
- 목록(태그·저자·스택)은 칩. Enter 로 추가하고 × 로 지운다 — 쉼표 규칙을 외우게 하지 않는다
- 열거형은 선택지. 값이 아니라 사람이 읽는 이름을 보여준다
- 필수/선택을 라벨 옆에 표시한다

## 접근성 (GR-7)

- 시맨틱 태그 우선 (`<nav>`, `<main>`, `<article>`, `<time>`)
- **내비게이션·검색·테마는 키보드만으로 완주 가능**해야 한다
- 검색을 열면 포커스가 입력으로 이동하고, Esc 로 닫힌다 (스펙 S-1, S-6)
- 본문 대비 4.5:1 이상, 큰 텍스트 3:1 이상 — **양쪽 테마 모두**
- 모든 이미지에 의미 있는 `alt` (장식이면 `alt=""`)
- 포커스 링을 제거하지 않는다

`/ui-verify` 가 렌더 결과에서 이 항목들을 점검한다.

## 조판 어휘 (2026-09-09)

배치가 좌측 목차로 바뀌면서 화면 전체가 쓰는 **공통 어휘**를 정했다.
새 화면을 만들 때 이 셋 밖으로 나가지 않는다 — 페이지마다 다른 장치를 쓰면 한 사이트로 안 읽힌다.

| 어휘 | 쓰는 곳 | 클래스 |
|---|---|---|
| **eyebrow** — 제목 위 작은 대문자 라벨 | 페이지·상세 머리, 실적 표 항목명 | `.eyebrow` |
| **rule-trail** — 제목과 도구 사이를 잇는 가는 괘선 | 섹션 제목, 상세 소제목 | `.rule-trail` |
| **hanging-index** — 걸린 두 자리 번호 | 목차, 목록 항목, 섹션 번호 | `.hanging-index` |

이모지는 쓰지 않는다. 서체와 따로 놀아 크기가 제각각이고, 어느 도구에서나 본 화면이 된다.

굵기 규칙: 페이지 제목 아래는 `border-foreground` 2px, 그 밖의 구분선은 `border-border` 1px.
가장 굵은 선이 한 화면에 하나만 있어야 그게 제목이라는 신호가 된다.
