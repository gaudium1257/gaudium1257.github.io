# RELIABILITY.md — 빌드, 배포, 복구

## 배포 대상

GitHub Pages. 리포지터리 `gaudium1257/gaudium1257.github.io` **전체가 곧 사이트**다.
앱은 하나이므로 배포도 하나다 — 관리자 모드는 같은 번들 안에 있다 ([ADR-0004](design-docs/adr/0004-single-app-admin-mode.md)).

배포 소스는 **GitHub Actions** 로 설정한다 (Settings → Pages → Source: GitHub Actions).
빌드 산출물을 커밋하지 않는다 — 소스와 `content/` 만 커밋한다.

## 파이프라인

```
push  →  CI: npm run verify  →  npm run build  →  Pages 배포
                                                      │
관리자 모드 커밋 ──────────────────────────────────────┘
   (Contents API) 도 같은 파이프라인을 탄다
```

`verify`가 실패하면 배포하지 않는다. **이것이 유일한 차단 게이트다.**

**콘텐츠 변경도 배포다.** 관리자 모드에서 게시하면 커밋이 생기고, Actions 가 돌고,
약 1분 뒤 공개 반영된다. 관리자 UI 는 이 지연을 사용자에게 알려야 한다.

## 머지 철학

에이전트 처리량이 사람의 주의력을 넘어서면, **긴 차단 게이트가 오히려 비용**이 된다.

- PR은 짧게 산다. 큰 변경은 나눈다
- 차단 게이트는 `verify` 하나로 유지한다. 게이트를 늘리기 전에 정말 필요한지 묻는다
- 고치는 비용이 싸고 대기 비용이 비싸면, 후속 수정으로 해결한다
- 단, **되돌리기 어려운 것**은 예외다. 앞에서 막는다:
  - 공개된 개인정보 (검색엔진이 이미 가져갔다고 가정한다)
  - 유출된 토큰 (되돌리기가 아니라 **폐기**가 답이다 — [SECURITY.md](SECURITY.md))

## 실패했을 때

1. **되돌린다.** 원인 분석보다 복구가 먼저다. 정적 사이트라 이전 커밋으로 되돌리면 끝이다
2. 재현되는 최소 케이스를 만든다
3. 고치고, **회귀 테스트를 추가한다**
4. 같은 실패가 반복 가능했던 이유를 `docs/`나 린트 규칙에 인코딩한다 (CB-9)

**콘텐츠 사고**(잘못 게시, 실수로 삭제)도 같다. `content/` 가 git 에 있으므로 `git revert` 로 복구된다.
이것이 콘텐츠를 리포지터리에 두기로 한 이유 중 하나다 ([ADR-0003](design-docs/adr/0003-content-store.md)).

## 관측

정적 사이트라 서버 로그가 없고, **분석 스크립트도 넣지 않는다** (토큰이 브라우저에 있으므로 —
[SECURITY.md §4](SECURITY.md)). 에이전트가 볼 수 있는 신호는:

- 브라우저 콘솔 에러 / 네트워크 실패 (`/ui-verify`가 수집)
- GitHub Actions 빌드 로그
- Playwright 스모크 테스트 결과
- 관리자 모드의 커밋 실패 응답 (권한 / 충돌 / 네트워크를 구분해 표시)

**콘솔 에러가 남은 상태를 "정상"으로 보고하지 않는다** (GR-4).
