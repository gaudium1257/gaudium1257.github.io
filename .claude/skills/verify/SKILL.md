# 검증 루프

**코드를 바꿨으면 검증한다. 예외 없다.** 검증 없이 "완료"라고 보고하지 않는다.

## 실행

```bash
npm run verify
```

이 명령은 다음을 순서대로 돌린다:

| 단계 | 명령 | 무엇을 지키는가 |
|---|---|---|
| 1. 타입 | `npm run typecheck` | INV-3, INV-4 |
| 2. 린트 | `npm run lint` | INV-4, INV-5, 포맷 |
| 3. 아키텍처 | `npm run lint:arch` | INV-1, INV-2 |
| 4. 문서 | `npm run lint:docs` | INV-9, INV-10 |
| 5. 테스트 | `npm run test` | 동작 회귀 |

빨리 좁히려면 개별 단계를 먼저 돌려도 된다. 단 **마지막엔 전체를 한 번 돌린다.**

## 실패했을 때 — 이렇게 고친다

에러 메시지는 고치는 방법을 함께 알려주도록 작성되어 있다 (CB-3). **먼저 끝까지 읽어라.**

| 실패 | 올바른 대응 | 금지 |
|---|---|---|
| 타입 에러 | 타입을 실제로 맞춘다 | `as any`, `@ts-ignore` (INV-4) |
| `lint:arch` 위반 | 코드를 올바른 레이어로 옮기거나 `src/shared/`로 승격 | 규칙 파일을 느슨하게 고치기 |
| 파일 예산 초과 | 파일/함수를 쪼갠다 | 예산 상향 |
| 테스트 실패 | 구현을 고친다 | 기대값만 바꾸기, `skip` (TESTING.md) |
| `lint:docs` 실패 | 색인 추가·링크 수정·문서 갱신 | 린트 대상에서 제외 |

**린트 규칙 자체를 고쳐야 한다고 판단되면**, 조용히 고치지 말고 사용자에게 근거와 함께 제안한다.
불변식 변경은 ADR 사안이다.

## UI를 바꿨다면

`verify`만으로는 부족하다. 이어서 `/ui-verify`를 실행한다.
"보기엔 맞을 것 같다"는 검증이 아니다 (CB-5).

## 아직 스캐폴드 이전이라면

애플리케이션 코드가 없으면 일부 단계가 "대상 없음"으로 통과한다.
이때 **통과를 성과로 보고하지 마라.** → [EP-0001](../../../docs/exec-plans/active/0001-bootstrap-scaffold.md)

## 보고 방식

- 통과했으면 어떤 단계가 통과했는지 사실대로 적는다
- 실패가 남았으면 **숨기지 말고 출력과 함께 보고**한다
- 일부만 돌렸으면 "일부만 돌렸다"고 명시한다
