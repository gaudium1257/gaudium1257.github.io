# 검증 루프

**코드를 바꿨으면 검증한다. 예외 없다.** 검증 없이 "완료"라고 보고하지 않는다.

## 실행

```bash
npm run verify
```

| 단계 | 무엇을 지키는가 |
|---|---|
| typecheck | INV-3, INV-4 |
| lint | INV-4, INV-5, 포맷 |
| lint:arch | INV-1, INV-2, INV-5, INV-8, **INV-9(스키마 단일 원천)** |
| lint:docs | INV-10, INV-11, CB-2 |
| test | 동작 회귀 |

빨리 좁히려면 개별 단계를 먼저 돌려도 된다. 단 **마지막엔 전체를 한 번 돌린다.**

## 실패했을 때 — 이렇게 고친다

에러 메시지는 고치는 방법을 함께 알려주도록 작성되어 있다 (CB-3). **먼저 끝까지 읽어라.**

| 실패 | 올바른 대응 | 금지 |
|---|---|---|
| 타입 에러 | 타입을 실제로 맞춘다 | `as any`, `@ts-ignore` (INV-4) |
| `lint:arch` 레이어 위반 | 코드를 올바른 레이어로 옮긴다 | 규칙 파일을 느슨하게 고치기 |
| `lint:arch` 스키마 위반 (INV-9) | 타입을 `shared/content` 로 옮기고 앱은 import 만 한다 | 앱에서 타입 재정의 |
| 파일/함수 예산 초과 | 쪼갠다 | 예산 상향 |
| 테스트 실패 | 구현을 고친다 | 기대값만 바꾸기, `skip` |
| `lint:docs` 실패 | 색인 추가·링크 수정·문서 갱신 | 린트 대상에서 제외 |

**린트 규칙 자체를 고쳐야 한다고 판단되면**, 조용히 고치지 말고 사용자에게 근거와 함께 제안한다.
불변식 변경은 ADR 사안이다.

## 두 앱이라 놓치기 쉬운 것

- **한쪽 앱만 고치고 끝내지 않았는가.** 공유 스키마를 바꿨으면 양쪽이 다 통과해야 한다
- viewer 에 쓰기 경로가 생기지 않았는가 (INV-8)

## UI 를 바꿨다면

`verify` 만으로는 부족하다. 이어서 `/ui-verify` 를 실행한다.
"보기엔 맞을 것 같다"는 검증이 아니다 (CB-5).

## 아직 스캐폴드 이전이라면

애플리케이션 코드가 없으면 일부 단계가 "대상 없음"으로 건너뛴다.
이때 **건너뛴 것을 통과로 보고하지 마라.** → [EP-0001](../../../docs/exec-plans/active/0001-bootstrap-scaffold.md)

## 보고 방식

- 통과했으면 어떤 단계가 통과했는지 사실대로 적는다
- 실패가 남았으면 **숨기지 말고 출력과 함께 보고**한다
- 일부만 돌렸으면 "일부만 돌렸다"고 명시한다
