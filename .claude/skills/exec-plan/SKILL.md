# 실행 계획 관리

계획은 일급 아티팩트다 (CB-4). 대화에만 남은 계획은 존재하지 않는다.

## 먼저 판단: 문서 계획이 필요한가

| 상황 | 조치 |
|---|---|
| 파일 1~2개, 되돌리기 쉬움 | **이 스킬을 쓰지 마라.** 그냥 하고 끝낸다 |
| 파일 3개 이상 / 새 도메인 / 레이어 경계 변경 | 실행 계획 문서 작성 |
| 아키텍처·스택·저장 방식 변경 | 실행 계획 **+** ADR (`docs/design-docs/adr/0000-template.md`) |

애매하면 쓴다.

## 새 계획 만들기

1. `docs/exec-plans/index.md`를 읽어 **다음 번호**를 정한다 (번호 재사용 금지)
2. `docs/exec-plans/TEMPLATE.md`를 `docs/exec-plans/active/NNNN-<slug>.md`로 복사해 채운다
3. 채울 때 지킬 것:
   - **목표**는 관찰 가능한 결과로. "리팩터링한다"가 아니라 "X가 Y 없이 동작한다"
   - **완료 조건**은 체크 가능하게. `npm run verify` 통과를 반드시 포함
   - **범위 밖**을 반드시 채운다. 비워두면 범위가 새어나간다
   - **미해결 질문**에 사용자 확인이 필요한 것을 모은다
4. `docs/exec-plans/index.md` 표에 행을 추가한다 (누락 시 `npm run lint:docs` 실패)
5. 관련 스펙/ADR이 `DRAFT`나 `OPEN`이면 **계획에 그 사실을 명시**하고, 그 위에 큰 구현을 쌓지 않는다

## 진행 중 갱신

- 단계를 마칠 때마다 체크박스를 갱신한다. 한꺼번에 몰아서 하지 않는다
- 판단을 내렸으면 **결정 로그**에 `날짜 | 결정 | 이유` 한 줄을 남긴다
- 계획과 다르게 가야 하면 계획을 먼저 고친다. 조용히 다르게 하지 않는다
- 막히면 상태를 `BLOCKED`으로 바꾸고 **무엇 때문에 막혔는지** 적는다 (CB-6)

## 완료 처리

1. 모든 완료 조건 체크 확인. `npm run verify` 통과 확인
2. **잔여 작업을 `docs/exec-plans/tech-debt-tracker.md`에 등록**한다
   — 말없이 사라진 항목이 드리프트의 시작이다
3. 관련 문서 갱신 (INV-9): `ARCHITECTURE.md` 도메인 표, `QUALITY_SCORE.md`, 스펙 상태
4. 파일을 `docs/exec-plans/completed/`로 옮기고, 상태를 `DONE`으로, `index.md`를 갱신한다
5. 지속되는 결정이 있었다면 ADR로 승격한다

## 안티패턴

- 계획을 쓰고 읽지 않기 — 각 단계 시작 전에 다시 연다
- 완료 조건에 "잘 동작한다" 같은 검증 불가능한 문장 넣기
- 계획 없이 5단계짜리 작업을 시작해서 중간에 컨텍스트를 잃기
