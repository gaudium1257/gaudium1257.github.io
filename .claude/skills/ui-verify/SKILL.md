# UI 실물 검증

사람의 QA 시간이 병목이다. **애플리케이션을 직접 읽어서 스스로 검증한다** (CB-5).
"코드상 맞으니 잘 나올 것"은 검증이 아니다.

## 실행

1. 개발 서버를 띄운다 — `mcp__Claude_Browser__preview_start` 에
   `.claude/launch.json` 의 `viewer` 또는 `admin` 을 넘긴다
2. 바꾼 화면으로 이동한다
3. 아래 점검표를 **전부** 돌린다

## 점검표

### 1. 렌더 확인 (스크린샷보다 먼저)
`read_page` 로 접근성 트리를 읽는다. 스크린샷은 눈으로 봐야 할 때만.
- 기대한 텍스트/역할(role)이 실제로 존재하는가
- 빈 상태·로딩 상태가 흉하게 남아 있지 않은가

### 2. 콘솔 에러 — **필수**
`read_console_messages` 로 확인한다.
**에러가 하나라도 남아 있으면 "동작한다"고 보고하지 않는다** (GR-4).
React key 경고, hydration 경고, 404 도 에러로 취급한다.

**주의**: 콘솔 버퍼에는 이전 탐색의 에러가 남는다. 고친 뒤에는 **새 탭에서** 확인한다.

### 3. 네트워크와 상태 코드
`read_network_requests` 로 실패 요청을 확인한다.
**배포 환경에서는 화면이 떠도 HTTP 상태가 틀릴 수 있다** — 딥링크는 상태 코드를 실측한다.

### 4. 상단 배너 (스펙: navigation-shell.md)
- 5개 탭 이동, **현재 탭 표시**가 보이는가 (N-1)
- **검색**: 열기 → 포커스 이동 → 입력 → 결과 → `?q=` URL 반영 → Esc 닫기 (S-1~S-6)
- **테마**: 토글 즉시 반영, 재방문 유지 (T-1~T-3)

### 5. 반응형
`resize_window` `preset: "mobile"` → 다시 `"desktop"`.
- **가로 스크롤이 생기지 않는가** (`scrollWidth === clientWidth` 로 실측)
- 배너 탭이 깨지지 않는가 (N-4)
- **끝나면 반드시 `desktop` 으로 되돌린다**

### 6. 테마 양쪽 (T-5)
`resize_window` `colorScheme` 로 light/dark 각각 확인한다.
**하드코딩된 색은 여기서 드러난다** — 한쪽 테마에서만 안 보이는 텍스트를 찾는다.

### 7. 접근성 (GR-7)
- 인터랙티브 요소가 `read_page filter:"interactive"` 에 role 과 이름을 갖고 나타나는가
- **배너의 세 도구를 키보드만으로 조작할 수 있는가** (N-5)
- 이미지에 alt 가 있는가

## 사용자에게 보고할 때

- 스크린샷은 **바뀐 부분**만. 전체 페이지 스크린샷을 남발하지 않는다
- 발견한 문제는 고친 뒤 다시 검증하고, **고치기 전/후를 함께** 보고한다
- 점검표 중 못 돌린 항목이 있으면 그렇다고 명시한다

## 안티패턴

- 스크린샷 한 장 찍고 "잘 나옵니다" — 콘솔·반응형·테마를 안 본 것이다
- 콘솔 에러를 보고도 "기존에 있던 것"이라며 넘어가기 → tech-debt-tracker 에 등록한다
- JS 를 실행해 DOM 을 고쳐놓고 통과시키기 → 검증이 아니라 조작이다. 소스를 고쳐라
- 라이트 모드만 보고 끝내기 → 다크 모드는 별개의 화면이다
